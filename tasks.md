## P0 — Bugs (root causes proven)

- [x] **T0 ⬆ Build fails from folders with spaces/commas** (the user's case). Branch `fix/build-paths`, merged into the personal branch and pushed to the fork; PR text in the workspace's `reference\github-drafts\pr-fix-build-paths.md`.
      * The C# build events (`AntiDupl.NET.WinForms.csproj:43` → `CopyData.cmd`, `AntiDupl.NET.Core.csproj:75` → `External.cmd`) quote their paths; both scripts take `%~1`/`%~2` and quote every expansion.
      * A comma also broke the Release link: `link.exe` cuts the `/LTCGOUT` (.iobj) and incremental-LTCG (.ipdb) paths at a comma (C1083 / LNK1104), and only for plain-ASCII paths. Release|x64 uses plain `/LTCG` without `/LTCGOUT`.
      * Tested: unmodified master fails, the fix builds (x64 Release, DLL loads, all resources copied) under `…\Coding, etc\Claude Code\Anti-Dupl\AntiDupl.NET`, `C:\ad\T0 x, y` and a folder named ``T0 [a] (b) & c, d=e! ^f ~g #h +i @j {k} $l 'm' `n é 日本 😀``. Still unsupported, by MSBuild/vcpkg themselves: `%` (MSBuild's temporary batch files, vcpkg's MSBuild integration) and `;` (MSBuild's list separator). A `$` followed by letters builds, but vcpkg's MSBuild integration writes its compiler-hash cache file to a path with that part dropped. vcpkg can't build its MSBuild-based ports (Simd) under a path with a comma: `vcpkg_install_msbuild` passes `/p:VcpkgInstalledDir=<install folder>` unescaped and MSBuild splits it at the comma. Such a checkout builds only while vcpkg's binary cache already holds those packages.
- [x] **T1 ⬆ TurboJPEG decodes red/blue swapped.** Branch `fix/turbojpeg-bgra` (with T3), merged into the personal branch. `TJPF_RGBA` → `TJPF_BGRA` in `src/AntiDupl/adTurboJpeg.cpp:59`. Checked with `plan/tools/core_search.py` on `Examples\`: both "Identical" pairs 1e-6 (pixels equal, only the CRC epsilon; shown `0.00`), "Different" 0.00026, at 32 and 128 px; with *Use libjpeg-turbo* off the values are bit-identical, so GDI+ and libjpeg-turbo decode these files the same. Previews of JFIF JPEGs under paths of 260 characters or more (upstream #122, #236), which the preview loads through the core (`PictureBoxPanel` → `BitmapWorker.LoadBitmap` → `adLoadBitmapW`, given the `\\?\` path a search result carries) with *Use libjpeg-turbo* on: the same pixels as a GDI+ decode of the file; upstream's build gives them red and blue swapped. → [01 § A](plan/01-difference-correctness.md)
- [x] **T2 ⬆ JPEG decoder chosen by the 4th byte.** Branch `fix/jpeg-routing`, merged into the personal branch. `TTurboJpeg::Supported` accepts any `FF D8 FF`; GDI+ decodes what TurboJPEG can't (before, such files were dropped without a defect entry); `TGdiplus::LoadExif` fills the EXIF fields of TurboJPEG-decoded images. Checked with `plan/tools/make_jpeg_cases.sh` + `core_search.py --details`: same-pixel pairs that differ only in their first segment (4:4:4/4:2:2/4:2:0/4:4:0, gray, progressive, arithmetic) are pixel-identical up to T4's float noise; all seven EXIF fields filled, also for JFIF files with EXIF (empty before with *Use libjpeg-turbo* on); a CMYK JPEG still loads (removing the fallback makes it vanish); a truncated one gets the same defect entry. Reading EXIF through GDI+ costs no measurable time; EXIF JPEGs load faster than through GDI+. With T1 in place, GDI+ and TurboJPEG decode all these cases alike. Upstream: merge after T1 (#246) — on its own it sends more JPEGs through the swapped decoder. → [01 § B](plan/01-difference-correctness.md)

- [x] **T6 ⬆ Janky sorting** (upstream #241). Branch `fix/sorting`, merged into the personal branch. Each pair from a search or a results file puts the lesser path first. Pair sorts (difference, group, hint …) keep the sides; ties → first path → second path → difference → id, ascending. A total order, so `std::sort` stays; display sorts compare digit runs by value (own `TPath::NaturalCompare` on the upper-cased paths instead of `StrCmpLogicalW`: no allocation per comparison, no new library; punctuation keeps code-unit order, unlike Explorer). Checked with `plan/tools/sort_check.py`: all checks pass, none on upstream. Still to see in the GUI: the test in [03 § I](plan/03-ui-bugs.md). → [03 § I](plan/03-ui-bugs.md)

- [x] **T8 ⬆ "0 means pixel-identical".** Branch `feat/pixel-identity`, merged into the personal branch. `0` = byte-identical, `1e-6` = pixel-identical, `≥ 1e-4` = different; threshold 0 % = pixel-identical only. Each image's decoded pixels get an XXH3-64 hash (BGRA rows; JXL's RGBA and HEIF's RGB converted row by row, so the same pixels hash alike in every format; vcpkg `xxhash`, header-only), stored in the image database (`FILE_VERSION` 6: older records decoded again; with `fix/db-upgrade-save` saved once after). Both comparers give 0 only for the same hash and size, otherwise at least `MIN_DIFFERENCE_OF_DIFFERENT_PIXELS` 1e-4, then the threshold. Turned/mirrored copies of the transformed search have no hash. Checked with `plan/tools/make_identity_cases.sh` + `core_search.py`, SSIM and mean square: byte copy 0; metadata strip, lossless progressive, JPEG vs PNG of its decoded pixels, PNG vs lossless JXL 1e-6 (also at 0 %); one changed pixel 1.01e-4, gone at 0 % (upstream: 1e-6, kept); through a version-5 database upgraded once and then read from the cache, the same values.
