## P0 — Bugs

- [ ] **T50 ⬆ Animated images with the same first frame show 0.00 (orange)**: the core decodes only a GIF's first frame (GDI+), and the pixel hash that allows 0.00 covers only that frame, so two animations that share it, or an animation and a still of its first frame, show as the same image. Reproduced with generated GIFs through `plan/tools/core_search.py` (SSIM and local colour). Fix: the pixel hash also covers every later frame of an animated file (GDI+ `GetFrameCount`/`SelectActiveFrame` for GIF; WebP, AVIF and any other loader that reads animations likewise), so a re-encoded copy of the same animation still shows 0.00. Comparing other frames is S7.
- [ ] **T51 Rows repeat while scrolling the results** (user's report): in the horizontal view, scrolling up sometimes paints the row that was on top before the scroll over all the visible rows below it while the scroll lasts. Not yet known whether scrolling down or the vertical view does it too.
- [ ] ~~**T52 ⬆ Changing the selected row got slower**~~ (reported by a maintainer on PR #280; upstream's current build, not that PR): going from one selected row to another takes noticeably longer than in v2.3.13. Not reproduced: with `plan/tools/ui_row_change_timing.ps1` on lists of one picture copied six times, upstream's current build and v2.3.13 take the same per row change, by key and by click, in both views (about 80 ms for a 1920 × 1129 JPEG, 530 ms for a 4000 × 2800 one, on this PC), also with highlighting on (about twice as long in both) and in the dark theme (a few ms more). PR #280's build takes the same as upstream's. The personal build's perceptual highlight (*Ignore compression noise*, not in any PR) holds a row change up less than the grey one (about 75 ms against 160 with the slightly different copies of one 1920 × 1129 picture), since its maps are computed on a background thread and drawn when ready (`adAlignedDifferenceMaps` about 80 ms for that pair, 185 ms at 4000 × 2800). A mixed list did look three times slower, but only because the builds sort it differently, so other pictures sat on the rows timed. Waiting on the maintainer's answer to what their setup is (build, view, list length, picture sizes, highlighting); then time that setup, and bisect upstream's merges if it differs.
