## P0 — Bugs (root causes proven)

- [x] **T0 ⬆ Build fails from folders with spaces/commas** (the user's case). Branch `fix/build-paths`, merged into the personal branch and pushed to the fork; PR text in the workspace's `reference\github-drafts\pr-fix-build-paths.md`.
      * The C# build events (`AntiDupl.NET.WinForms.csproj:43` → `CopyData.cmd`, `AntiDupl.NET.Core.csproj:75` → `External.cmd`) quote their paths; both scripts take `%~1`/`%~2` and quote every expansion.
      * A comma also broke the Release link: `link.exe` cuts the `/LTCGOUT` (.iobj) and incremental-LTCG (.ipdb) paths at a comma (C1083 / LNK1104), and only for plain-ASCII paths. Release|x64 uses plain `/LTCG` without `/LTCGOUT`.
      * Tested: unmodified master fails, the fix builds (x64 Release, DLL loads, all resources copied) under `…\Coding, etc\Claude Code\Anti-Dupl\AntiDupl.NET`, `C:\ad\T0 x, y` and a folder named ``T0 [a] (b) & c, d=e! ^f ~g #h +i @j {k} $l 'm' `n é 日本 😀``. Still unsupported, by MSBuild/vcpkg themselves: `%` (MSBuild's temporary batch files, vcpkg's MSBuild integration) and `;` (MSBuild's list separator). A `$` followed by letters builds, but vcpkg's MSBuild integration writes its compiler-hash cache file to a path with that part dropped. vcpkg can't build its MSBuild-based ports (Simd) under a path with a comma: `vcpkg_install_msbuild` passes `/p:VcpkgInstalledDir=<install folder>` unescaped and MSBuild splits it at the comma. Such a checkout builds only while vcpkg's binary cache already holds those packages.
- [x] **T1 ⬆ TurboJPEG decodes red/blue swapped.** Branch `fix/turbojpeg-bgra` (with T3), merged into the personal branch. `TJPF_RGBA` → `TJPF_BGRA` in `src/AntiDupl/adTurboJpeg.cpp:59`. Checked with `plan/tools/core_search.py` on `Examples\`: both "Identical" pairs 1e-6 (pixels equal, only the CRC epsilon; shown `0.00`), "Different" 0.00026, at 32 and 128 px; with *Use libjpeg-turbo* off the values are bit-identical, so GDI+ and libjpeg-turbo decode these files the same. Still to see in the GUI: previews of JFIF JPEGs under >260-char paths (upstream #122, #236). → [01 § A](plan/01-difference-correctness.md)
- [x] **T2 ⬆ JPEG decoder chosen by the 4th byte.** Branch `fix/jpeg-routing`, merged into the personal branch. `TTurboJpeg::Supported` accepts any `FF D8 FF`; GDI+ decodes what TurboJPEG can't (before, such files were dropped without a defect entry); `TGdiplus::LoadExif` fills the EXIF fields of TurboJPEG-decoded images. Checked with `plan/tools/make_jpeg_cases.sh` + `core_search.py --details`: same-pixel pairs that differ only in their first segment (4:4:4/4:2:2/4:2:0/4:4:0, gray, progressive, arithmetic) are pixel-identical up to T4's float noise; all seven EXIF fields filled, also for JFIF files with EXIF (empty before with *Use libjpeg-turbo* on); a CMYK JPEG still loads (removing the fallback makes it vanish); a truncated one gets the same defect entry. Reading EXIF through GDI+ costs no measurable time; EXIF JPEGs load faster than through GDI+. With T1 in place, GDI+ and TurboJPEG decode all these cases alike. Upstream: merge after T1 (#246) — on its own it sends more JPEGs through the swapped decoder. → [01 § B](plan/01-difference-correctness.md)
- [x] **T3 ⬆ Stale image database.** On `fix/turbojpeg-bgra`. `FILE_VERSION` 4 → 5; older records keep type/size/CRC/defect but are marked unfilled with blockiness/blurring unknown. Also needed, missing from the first design: `FillPixelData` resets the plane's cached mean and variance, which the SSIM comparer only computes while they are 0 — without it a version-4 database gave 1e-6 for the "Different" pair and 0.61 for an "Identical" one. With T4 merged the comparer no longer reads those cached floats, so the personal branch drops that reset (an old database still gives the same values as a fresh one). Checked: a database written by the unmodified core, read by the fixed one, gives the same values as a fresh one. Later per-image format changes (T4, T8, T10) need another bump, each costing one re-scan. → [01 § C](plan/01-difference-correctness.md)

- [x] **T4 ⬆ Float noise in SSIM** (identical planes → 7.6e-6 or 1.5e-5; not green, dropped at 0 %; upstream #186). Branch `fix/ssim-exact`, merged into the personal branch. Exact integer `sum`/`sumSquare` per plane, filled once per search in `FillOther` (the compare threads only read them); equal planes detected exactly by `correlation sum == both sums of squares`, otherwise SSIM in double. No file-format change: `average`/`varianceSquare` are still filled and saved. `/fp:fast` stays, since the integer test doesn't depend on rounding. Checked with `core_search.py` on 46 files with byte-identical copies in a second folder: before, some copies got 7.6e-6/1.5e-5 and were missing at threshold 0 (both sizes, upstream and T1 builds); after, all exactly 0, also over repeated runs and through the image database. Other pairs change by rounding only. → [01 § D](plan/01-difference-correctness.md)
